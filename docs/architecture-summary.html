Multi-Agent Trading Pipeline

Architecture summary — sequential pipeline extension to the dual-MCP stock agent (Massive.com + Robinhood)

1. Overview

A pipeline of independent agents, each handling one stage of trade research, feeding forward into the next stage. Agents within a stage run in parallel and independently per candidate, to avoid correlated bias. Every agent outputs structured reasoning alongside its verdict, not just a pass/fail, so a retrospective feedback loop can trace where judgment broke down.

4. Key Design Principles

  • Sequential between stages, parallel and independent within a stage — each candidate gets its own unbiased pass, with no cross-comparison at the technical stage.
  • Each agent receives the prior agent's report and the raw data behind it, so a bad upstream filter doesn't fully blind the next stage.
  • Fundamental worthiness and technical tradeability are uncorrelated filters — rejecting a fundamentally strong company on chart grounds is a normal outcome, not an error.
  • Every agent logs structured reasoning (what pushed it toward/away from its conclusion), not just a verdict — this is the backbone of the feedback loop.
  • The middleware (formerly "orchestrator") is one-directional: it reports pipeline output to the user, but the user's manual accept/reject never feeds back into the system as if it were the system's own judgment. This keeps user bias out of the self-improvement loop.
  • Meta-review is split into two decoupled agents — an outcomes agent (pure financial results, no judgment) and a process agent (reasoning quality, including whether foreseeable risks like macro exposure were accounted for) — so a well-reasoned trade that loses to a genuine black swan isn't penalized the same as a missed, foreseeable risk.
  • Targeting swing / long-term horizons, not day trading — this makes cross-stage data staleness a non-issue.

5. Open Decisions

Agent 1 output format: ranked list with potential scores (gives the feedback loop gradient signal, lets downstream agents triage) vs. a simple black-and-white pass/fail list. Not yet decided.
Running confidence score: considering a score that travels with each candidate through the whole pipeline (rather than a fresh yes/no per stage), so its trajectory across stages helps trace which agent introduced doubt — aiding attribution when a trade fails for reasons that aren't a single clean-cut agent error.

6. Data Requirements

Every category below needs both a live/current version (to run the system) and a deep historical version (to back test it honestly):

  • Price and volume data
  • Sector-level performance / breadth
  • News and catalyst events (earnings, FDA approvals, analyst actions)
  • Company fundamentals (financials, filings, ownership, valuation)

Already covered

  • Massive.com MCP — historical OHLCV, technical indicators, pivot support/resistance (feeds the Technical Analysis Agent)
  • Robinhood MCP — live quotes, account data, positions (feeds the Middleware's visibility layer)

Open gaps

  • Live and historical sector-level screening / breadth data
  • A historical news and catalyst archive tied to specific dates — flagged as the hardest to source and the most important for honestly back testing Agent 1's catalyst-based picks

7. Overall Assessment

Architecture: mature and well-reasoned — decoupled independent stages, raw-data pass-through, structured reasoning logs, and a hard separation between system analysis and human decision-making.

Will it make money: unclear and shouldn't be assumed — a good pipeline architecture doesn't guarantee good market calls. The value of this design is that it's honest and falsifiable: back testing and the process agent will surface whether the underlying judgment is actually good, rather than letting bad calls hide.

Overfitting risk: back testing/tuning against historical data too tightly risks the system memorizing the past rather than reasoning about the future. Mitigate with a held-out validation period the system was never tuned against, and lean on the process agent (reasoning quality, not just outcome) as a check against optimizing toward the wrong signal.

Technical complexity: manageable — this is agent orchestration with distinct prompts and data access per stage, not novel ML. A working first version is realistic in weeks; tuning it to be reliably good will take many iterations of back testing and refinement.

Verdict: worth building as a rigorous research/learning project. Expect early versions to be mediocre or lose money — that's the system doing its job by surfacing weak reasoning, not a failure of the architecture.
